Tests, Allies & Enemies

The AI Threat Model

Prompt Injection
Adversarial inputs that manipulate model behavior, exfiltrate data, or bypass safety filters.
Token Abuse
Unauthorized callers burning through expensive compute. One compromised pod = $10K overnight.
Model Scraping
Systematic extraction of model weights or behavior through repeated inference queries.
Lateral Movement
Compromised workloads pivoting to AI services. Flat networks make this trivial.
Walk through each threat with a concrete example. Prompt injection is the headline risk, but lateral movement via AI services is the one most teams miss. "Being inside the cluster should not equal trust."

The Approach

Four Patterns
That Actually Work

From identity to observability—a layered defense for AI workloads in Kubernetes.

01 Identity-First Security
SPIFFE / mTLS — workload identity over network trust
02 East-West Controls

03 AI-Specific Isolation

Set up the four technical pillars. Each gets its own deep-dive slide. This is the roadmap for the rest of the talk. Deliver these as "actionable patterns you can implement this week."

Pattern 01

Identity-First
Security

  • Workload identity > network-based trust
  • SPIFFE provides cryptographic identity
  • mTLS ensures both sides prove who they are
  • No identity = no access
Show the simple model: Service A has identity, gets through. Unknown pod has no identity, blocked. "The question isn't where are you in the network — it's who are you." You can talk about SPIFFE/SPIRE conceptually here without running it live.

Pattern 02

Controlling
East-West Traffic

  • Default deny — then explicitly allow
  • Namespace is not a security boundary
  • Egress control is the most commonly missed piece
  • Cilium NetworkPolicy for L3/L4 + L7
# Default deny on model server
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: default-deny-model
  namespace: ai-demo
spec:
  endpointSelector:
    matchLabels:
      app: model-server
  ingress: []
  egress: []
"Network policy without egress thinking is one of the most common false wins in Kubernetes security." Keep the YAML minimal — audience should see default deny + explicit allow. That's enough. Don't overload with YAML on slides.

Pattern 03

Isolating
AI Systems

  • Model server in dedicated namespace
  • Only approved identities can call inference
  • Separate prompt/data flow from general traffic
  • Label-driven policy enforcement
# Only trusted-client reaches the model
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-trusted-to-model
  namespace: ai-demo
spec:
  endpointSelector:
    matchLabels:
      app: model-server
  ingress:
    - fromEndpoints:
        - matchLabels:
            app: trusted-client
      toPorts:
        - ports:
            - port: "8080"
This is the "money slide" in YAML form. Only trusted namespace, only trusted client, only port 8080. "Not all services should see the model." This directly sets up the demo.

Pattern 04

Observability
That Matters

Controls are only real if you can verify and monitor them.

  • Latency anomalies signal compromise
  • Token spikes signal abuse
  • Access pattern changes signal lateral movement
  • Hubble shows allowed & denied flows
# Watch denied traffic in real time
$ hubble observe --verdict DROPPED

# Output:
DROPPED untrusted/untrusted-client
    -> ai-demo/model-server:8080
    policy-verdict:DENIED

DROPPED untrusted/attacker
    -> ai-demo/model-server:8080
    policy-verdict:DENIED

# This is what defenders want to see.
This slides ties directly to the demo. Hubble's dropped flow view is powerful because it makes the policy visible. "Not just logs — latency anomalies, token spikes, access patterns." Show that security is verifiable, not just declarative.

Phase 1 — The Startup Default

Everything Can Talk
to Everything

No policies. No identity checks. Internal cluster access = implicit trust.

# Deploy insecure workloads
$ make deploy-insecure

# Test from every pod
$ make test-insecure

trusted-client   -> model-server  ✓ 200 OK
untrusted-client -> model-server  ✓ 200 OK
attacker          -> model-server  ✓ 200 OK

# Everyone gets in. That's the problem.
"This is what happens when internal cluster access becomes implicit trust." All three succeed — that's exactly the point. The attacker pod with curl can hit your model inference endpoint. Pause here to let it sink in.

Phase 2 — Guardrails Applied

Only Approved
Identities Get Through

"I'm not adding friction to developers. I'm defining which identities are allowed to talk to sensitive services."

# Apply secure policies
$ make deploy-secure

# Test again
$ make test-secure

trusted-client   -> model-server  ✓ 200 OK
untrusted-client -> model-server  ✕ TIMEOUT
attacker          -> model-server  ✕ TIMEOUT

# From network trust to policy-driven
# workload trust. That's the move.
This is your strongest live moment. Trusted succeeds, untrusted and attacker both fail. "This is the move from network location trust to policy-driven workload trust." Let the terminal output tell the story.

The Road Back

What Fails in Reality

✕ "We'll add mTLS later"
Later never comes. By the time you add it, you have 40 services and zero identity.
✕ "NetworkPolicies = done"
Ingress without egress is half a lock. DNS egress alone unlocks data exfiltration paths.
✕ "AI is just another microservice"
It has different threat profiles: IP exposure, cost abuse, prompt sensitivity, compute targets.
✕ "Security slows us down"
Only when it's bolted on. When it's infrastructure, it's invisible and instant.
Rapid-fire anti-patterns. Each one should land with a quick, punchy explanation. Don't dwell — move through them at pace. The audience should be nodding along recognizing their own patterns.

Return with the Elixir

What to Do
Monday Morning

01 Default deny. Today.
Start with CiliumNetworkPolicy or native NetworkPolicy. Lock down ingress and egress.
02 Treat AI workloads as sensitive infrastructure
Dedicated namespace, explicit access, labeled boundaries. Not just another deployment.
03 Make security the easy path
Platform abstractions, GitOps, opinionated defaults. Developers shouldn't have to think about it.
04 Observe, don't just declare
If you can't see it working, it's not working. Hubble, traffic logs, anomaly detection.
These should feel achievable. "You can do all four of these this week." Frame them as Monday morning actions, not aspirational goals. The audience should leave feeling empowered, not overwhelmed.
